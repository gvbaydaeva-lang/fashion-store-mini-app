# Тестовый заказ без оплаты и очистка интерфейса — план реализации

> **Для AI-агентов:** перед выполнением использовать `superpowers:subagent-driven-development` или `superpowers:executing-plans`. Каждый агент выполняет только свою задачу, проходит её чеклист и передаёт точный отчёт следующему reviewer-агенту.

**Цель:** сделать полноценный демонстрационный путь заказа из корзины без настоящей оплаты, сохранить в заказе все выбранные товары и варианты, не списывать остатки ошибочно и убрать из интерфейса лишние технические слова «Демо» и «сервер».

**Архитектура:** покупатель продолжает проходить путь `каталог → корзина → контакты → получение → проверка → подтверждение тестового заказа`. Сервер создаёт отдельный тестовый заказ и сохраняет его состав, но такой заказ не считается оплаченным, не попадает в рабочую очередь оплаченных заказов и не уменьшает остатки. Сетевая ошибка не превращается молча в «созданный заказ».

**Стек:** vanilla JavaScript, Node `node:test`, Supabase Edge Functions на TypeScript/Deno, PostgreSQL, Telegram Web App `initData`.

**Спецификация:** `README.md`, `ARCHITECTURE.md`, `brief.md`, текущий код `tg-app/` и `supabase/`.

## Глобальные ограничения

- Не подключать настоящую оплату, платёжного провайдера, webhook или онлайн-кассу.
- Не использовать `initDataUnsafe` для серверной авторизации.
- Не записывать и не выводить токены, секреты, настоящий Telegram ID или `initData`.
- Не скрывать настоящие ошибки полностью: технические детали заменять понятным безопасным сообщением.
- Все выбранные позиции корзины должны передаваться по `productId`, `variantId` и `quantity`.
- Тестовый заказ не является оплатой, резервом и подтверждением реальной покупки.
- Публикация товара, seller-доступ и уже работающие admin-функции не должны быть сломаны.
- После изменения кода обновить относящиеся `README.md`, `ARCHITECTURE.md`, `CHANGELOG.md` и `.env.example`, если меняется конфигурационный контракт.
- Не выполнять `git commit`, `git push` или publish без отдельного разрешения пользователя.

## Карта файлов

- `tg-app/app.js` — buyer checkout, состояние корзины/заказа и тексты экранов.
- `tg-app/api.js` — клиентский контракт `order-api` и безопасные ошибки.
- `tg-app/core.js` — чистая логика корзины и формирования локальных данных.
- `tg-app/tests/api.test.js` — клиентские API-тесты.
- `tg-app/tests/core.test.js` — тесты корзины и чистой бизнес-логики.
- `tg-app/tests/app-smoke.test.js` — статические проверки buyer runtime.
- `supabase/functions/order-api/index.ts` — серверная проверка Telegram и создание/чтение заказа.
- `supabase/migrations/20260902100000_orders.sql` — текущая схема заказов и RPC `create_order`.
- `supabase/functions/tests/` — серверные контрактные тесты.
- `README.md`, `ARCHITECTURE.md`, `CHANGELOG.md` — документация фактического поведения.

## Порядок и параллельность

1. Агент 1 сначала добавляет тесты и фиксирует текущее неправильное поведение.
2. После review задачи 1 параллельно можно запустить Агент 2 и Агент 3: они работают в разных подсистемах.
3. После Агентов 2 и 3 запускается Агент 4 для документации и полного gate.
4. Задачу о настоящей оплате в этом плане не выполнять.
