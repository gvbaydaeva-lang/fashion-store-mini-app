# Задания отдельным агентам: админ-панель и пользовательский каталог

Этот файл предназначен для поэтапной передачи задач отдельным агентам. Каждый новый агент получает только одну задачу. Следующего агента запускать только после того, как предыдущая задача прошла свой чеклист и отдельный review.

Основной план: `tg-app/docs/superpowers/plans/2026-09-02-admin-buyer-reliability.md`.

## Правила передачи задач

Перед каждым агентом:

1. Убедиться, что предыдущая задача отмечена как `APPROVED`.
2. Проверить `git status --short` и сохранить чужие незакоммиченные изменения.
3. Передать агенту только его блок ниже.
4. Не просить агента менять соседнюю задачу «заодно».
5. Не передавать секреты, реальные Telegram ID, токены, ключи Supabase или реальный `initData`.
6. После выполнения передать результат отдельному review-агенту.
7. Следующую задачу начинать только после отчёта review-агента со статусом `APPROVED`.

Общий обязательный текст для каждого implementer-агента:

```text
Ты выполняешь только одну задачу из проекта Tg_katalog.

Сначала прочитай AGENTS.md, README.md, ARCHITECTURE.md и указанные в задаче файлы. Не используй initDataUnsafe для авторизации. Не читай и не выводи секреты из .env. Не запускай других агентов. Не делай commit, push или publish без отдельного разрешения.

Работай по TDD: сначала добавь или измени тест, запусти его и зафиксируй ожидаемое падение, затем внеси минимальное исправление, повтори тест и полный gate.

После работы обязательно проверь собственный чеклист задачи. В отчёте укажи:
- STATUS: DONE, DONE_WITH_CONCERNS или BLOCKED;
- изменённые файлы;
- команды проверок и точный результат;
- каждый пункт чеклиста как PASS или FAIL;
- что не проверено;
- оставшиеся риски.
``` 

Общий обязательный текст для review-агента:

```text
Проверь только указанную задачу и её diff. Прочитай brief задачи, отчёт implementer-агента и изменённые файлы. Не исправляй код сам.

Дай два независимых вердикта:
1. SPEC: соответствует ли реализация требованиям задачи;
2. QUALITY: нет ли регрессий, ошибок безопасности, пропущенных тестов или лишних изменений.

Проверь весь чеклист задачи. Для каждого пункта напиши PASS или FAIL с доказательством: файл, строка, тест или команда. Итоговый статус: APPROVED, CHANGES_REQUIRED или BLOCKED. Если нужны изменения, перечисли их по приоритету.
```

```text
Проведи review задачи <N> проекта Tg_katalog. Прочитай основной план, только brief задачи <N>, отчёт implementer-агента и diff. Проверь SPEC и QUALITY отдельно. Не исправляй код.

Обязательно проверь каждый пункт чеклиста implementer-а, тесты до и после, отсутствие лишних изменений, отсутствие секретов, соответствие AGENTS.md и документации. Особое внимание: не выдавать HTTP smoke, обычный браузер или Node tests за реальный Telegram/device smoke.

Верни:
STATUS: APPROVED | CHANGES_REQUIRED | BLOCKED
SPEC: PASS/FAIL с доказательствами
QUALITY: PASS/FAIL с доказательствами
CHECKLIST: каждый пункт PASS/FAIL
FINDINGS: упорядоченный список конкретных проблем с файлами/строками
RECOMMENDATION: что должен сделать следующий implementer
```

## Финальный reviewer после Агентов 1–16

```text
Проведи полный review всей ветки после задач 1–16. Проверь основной план целиком, все task reports и полный diff от baseline. Не исправляй код.

Дай итог по четырём направлениям: админ-панель, buyer-каталог, серверная безопасность/данные, документация/release. Проверь итоговый чеклист основного плана построчно.

Статус может быть FINAL_APPROVED только если:
- удаление групп безопасно;
- save товара и изображений атомарен;
- buyer после seller-действий актуален;
- серверные ошибки безопасны;
- заказы и статусы не подделываются клиентом;
- тесты проходят;
- Telegram/device пункты имеют фактическое доказательство либо явно отмечены непроверенными;
- production SHA и live assets сверены.

Если есть замечания, верни FINAL_CHANGES_REQUIRED с точными файлами, строками и одним рекомендуемым агентом для исправления.
```
