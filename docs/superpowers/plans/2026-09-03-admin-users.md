# «Пользователи» в админ-панели — план реализации

## Зачем это нужно

После запуска акции «500 ₽» владелец магазина должен внутри закрытой админ-панели Telegram Mini App видеть не обезличенную цифру, а список реальных Telegram-пользователей, которые открыли приложение. Это нужно, чтобы понимать рост аудитории до появления полноценной аналитики продаж, оплаты и рассылок.

Этот документ описывает только первый самостоятельный этап — раздел **«Пользователи»**. Он не добавляет графики продаж, оплату, массовые рассылки или автоматические сообщения о заказах.

## Что уже есть и чего ещё нет

В проекте уже есть:

- закрытый режим продавца с серверной проверкой Telegram `initData`;
- `admin-api` для действий владельца;
- `order-api`, который создаёт серверный, но пока демонстрационный заказ;
- таблица `orders` с Telegram ID покупателя;
- `order-notifications`, который сейчас умеет уведомлять только владельца о подтверждённой оплате.

Пока нет:

- общей таблицы покупателей;
- учёта первого и последнего открытия Mini App;
- обработчика команды `/start` бота;
- списка пользователей в админ-панели;
- реальной оплаты и статуса `paid`;
- рассылок или уведомлений покупателю.

Следовательно, нельзя выдавать «заказ оформил» за «заказ оплатил», а «открыл Mini App» — за «запустил бота».

## Словарь показателей

| Что увидит владелец | Точное значение |
| --- | --- |
| Всего пользователей | уникальные Telegram-пользователи, хотя бы раз открывшие Mini App с проверенным `initData` |
| Присоединились сегодня | пользователи, у которых первое проверенное открытие произошло сегодня по Москве |
| Открывшие приложение | пользователи, у которых есть хотя бы одно проверенное открытие Mini App |
| Оформляли заказ | пользователи, у которых есть хотя бы один серверный заказ; до подключения оплаты он будет помечен как демонстрационный |
| Получили 500 ₽ | пользователи, успешно нажавшие кнопку получения бонуса в период акции |
| Запустили бота | отдельный показатель будущего этапа: появляется только после настройки bot webhook и получения `/start` |

## Рекомендованное решение

Оставить админку внутри существующего Mini App и добавить в неё отдельную верхнюю вкладку **«Пользователи»** рядом с «Товары» и «Заказы».

Данные сохраняются только на сервере Supabase:

```text
Покупатель открывает Mini App
        ↓ raw Telegram initData
user-api: сервер проверяет подпись и auth_date
        ↓
customers + customer_activity
        ↓
admin-api: list-users / get-user
        ↓
закрытая вкладка «Пользователи» владельца
```

Почему так:

- `localStorage` виден только на одном телефоне и не подходит для статистики;
- имя и username, присланные браузером без проверки, можно подделать;
- только сервер должен решать, является ли это новым пользователем и когда он впервые открыл приложение;
- обычный пользователь не должен читать список других покупателей.

## Данные, которые будут храниться

### Таблица `customers`

| Поле | Назначение |
| --- | --- |
| `telegram_user_id` | уникальный ID Telegram, основной ключ пользователя |
| `first_name` | имя из проверенных данных Telegram, может обновляться |
| `last_name` | фамилия, если Telegram её передал |
| `username` | `@username`, если он есть; поле необязательное и может меняться |
| `first_app_opened_at` | первое проверенное открытие Mini App |
| `last_app_opened_at` | последнее проверенное открытие Mini App |
| `bot_started_at` | будет заполнено позже, когда появится webhook бота |
| `marketing_opt_in_at` | будет заполнено позже, только после явного согласия на акции |
| `created_at`, `updated_at` | технические даты сервера |

В первой версии в карточке пользователя показываются имя, `@username` при наличии, даты первого и последнего открытия и отметка «Оформлял заказ». После отдельной реализации акции появится отметка «Получил 500 ₽». Телефон, адрес и другие данные не выводятся в этом разделе.

### Таблица `customer_activity`

Содержит только нужные события для подсчёта:

- `app_opened` — открытие Mini App;
- `bonus_claimed` — получение бонуса, после реализации акции;
- в будущем: `bot_started`, `marketing_opt_in`, `order_created`, `order_paid`.

Для открытия приложения вводится защита от лишних дублей: для одного пользователя сохраняется не более одного `app_opened` за календарный день по Москве. При этом `last_app_opened_at` в `customers` всё равно обновляется при каждом корректном открытии.

## Как будет выглядеть вкладка «Пользователи»

Вкладка не называется «Статистика», потому что расширенная статистика продаж — отдельный будущий модуль.

Вверху показываются четыре компактные карточки:

- «Всего пользователей»;
- «Сегодня присоединились»;
- «Открыли приложение»;
- «Оформляли заказ».

Ниже — поиск по имени или username и фильтры:

- все;
- сегодня;
- получили 500 ₽;
- оформляли заказ.

Список отсортирован по последнему открытию: сначала самые свежие. Одна строка пользователя содержит:

```text
Имя пользователя
@username или «Username не указан»
Присоединился: 03.09.2026, 14:25
Открывал: сегодня, 16:10
Метки: «500 ₽ получены» · «Есть заказ»
```

При нажатии открывается подробная карточка того же пользователя. Технический Telegram ID в обычном списке не показывается; при необходимости он может быть доступен владельцу в карточке через действие «Скопировать ID».

Пустое состояние должно честно говорить: «Пользователей пока нет. Они появятся после первого открытия приложения в Telegram». Ошибки сервера не показывают технический текст Supabase.

## Серверная часть

### 1. Миграция базы данных

Создать новую миграцию после существующих миграций заказов. Она должна:

- создать `customers` и `customer_activity`;
- добавить индексы для `first_app_opened_at`, `last_app_opened_at`, `event_type`, `occurred_at`;
- включить RLS;
- отозвать доступ к таблицам у `anon` и `authenticated`;
- дать доступ только `service_role` внутри Edge Functions;
- добавить ограничения на допустимые типы событий;
- сделать запись дневного `app_opened` идемпотентной.

### 2. Новая Edge Function `user-api`

Она принимает только raw `Telegram.WebApp.initData` и выполняет три покупательских действия:

- `track-open` — проверяет `initData`, создаёт или обновляет пользователя и сохраняет событие открытия;
- `get-profile` — возвращает покупателю только его собственный безопасный профиль;
- `claim-bonus` — следующий этап акции: проверяет период и однократно начисляет бонус.

`track-open` запускается после успешной инициализации Mini App внутри Telegram. Обычный браузер без Telegram не создаёт запись пользователя. Сам баланс 500 ₽ не хранится одной цифрой в `customers`: акция добавит отдельную историю бонусных начислений и списаний, чтобы не потерять причину и дату каждой операции.

### 3. Расширение `admin-api`

Добавить только действия владельца:

- `list-users` — карточки-счётчики, список, поиск, фильтр и пагинация;
- `get-user` — подробности одного пользователя.

Перед каждым из них сохраняется текущая проверка: raw `initData` → подпись Telegram → свежий `auth_date` → allowlist владельца. Никакой пользовательский ID не принимается как основание для доступа.

### 4. Связь с заказами

`list-users` определяет метку «Оформлял заказ» по серверной таблице `orders`, а не по данным браузера. До реальной оплаты она означает только «есть созданный заказ».

При дальнейшем подключении платежа в эту же модель добавится `order_paid`. Полноценный показатель выручки и графики намеренно не входят в этот этап.

## Порядок реализации

1. Написать тесты на серверный контракт и запрет доступа постороннему Telegram-пользователю.
2. Создать миграцию `customers` и `customer_activity`, проверить индексы, RLS, grants и уникальность дневного открытия.
3. Реализовать и протестировать `user-api.track-open` с проверкой raw `initData` и идемпотентностью.
4. Вызвать `track-open` из Mini App только после готовности Telegram SDK; браузерный режим не учитывается как пользователь Telegram.
5. Добавить в `admin-api` получение списка пользователей и одной карточки пользователя.
6. Добавить в админку вкладку «Пользователи», счётчики, поиск, фильтры, пустое состояние и безопасные ошибки.
7. Связать список с `orders`, показывая только факт созданного заказа без заявления об оплате.
8. Проверить ширины 320, 375 и 430 px, светлую и тёмную тему, отсутствие горизонтальной прокрутки и работу кнопки «Назад».
9. Применить миграцию и развернуть функции только после отдельного одобрения; проверить в настоящем Telegram на аккаунте владельца и на обычном пользовательском аккаунте.
10. Обновить документацию и выпустить изменения только после отдельного просмотра локального результата.

## Проверки, которые обязательны

- один пользователь открыл приложение десять раз за день → в списке один пользователь, «сегодня» не растёт десять раз;
- два разных Telegram-аккаунта → две разные строки;
- повторный сетевой запрос `track-open` не создаёт дубликат;
- пользователь без username корректно показывается;
- посторонний Telegram-пользователь получает `403` на `list-users` и `get-user`;
- владелец видит список только внутри Telegram с действительным `initData`;
- заказ есть, но демонстрационный → метка «Оформлял заказ», не «Оплатил»;
- на ширине 375 px длинные имена и username не выходят за экран;
- в браузере без Telegram пользователь не записывается как новый Telegram-покупатель.

## Что намеренно остаётся на потом

- экран «Статистика» с выручкой, средним чеком, конверсией и графиками;
- бот webhook и факт `/start`;
- источник перехода из Instagram или рекламы;
- согласие на маркетинговые рассылки;
- массовые рассылки;
- уведомления покупателю «заказ оформлен» и «готов к выдаче»;
- платёжный webhook, статус `paid` и автоматическое списание бонуса.

## Ручные действия после реализации

Перед production-проверкой владельцу потребуется в Supabase Dashboard безопасно добавить уже используемые серверные Secrets и, позднее для бота, настроить webhook с отдельным секретом. Значения токенов, ключей и Telegram ID не записываются в код, Git или этот документ.

## Критерий готовности первого этапа

После запуска акции владелец открывает внутри Telegram: **Магазин → Режим продавца → Пользователи** и видит:

- сколько уникальных пользователей присоединилось сегодня;
- общий список пользователей Mini App;
- Telegram-имя и username, если он существует;
- время первого и последнего открытия;
- получил ли пользователь 500 ₽;
- есть ли у пользователя созданный заказ.

При этом не появляется отдельный раздел продаж, не отправляется ни одна рассылка и не заявляется, что демонстрационный заказ оплачен.
