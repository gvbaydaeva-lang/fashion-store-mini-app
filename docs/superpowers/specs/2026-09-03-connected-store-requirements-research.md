# Связанный магазин в Telegram: исследование и обязательные требования

**Назначение файла:** это не план разработки и не инструкция «сразу писать код». Здесь зафиксировано, каким должен быть наш магазин после исследования удачных open-source решений и уже найденных ошибок проекта. Документ нужен как критерий для любых будущих изменений покупательского Mini App, админ-панели, заказов и оплаты.

**Граница:** мы не копируем чужой код, интерфейс, React/Next.js или чужие платёжные системы. Берём только архитектурные принципы, которые подходят текущему проекту: статический JavaScript Mini App + Supabase Edge Functions + PostgreSQL.

## 1. Что уже пошло не так в нашем проекте

| Наблюдение | Почему это проблема | Какого состояния больше не должно быть |
| --- | --- | --- |
| Демо-заказ сохранялся в `localStorage` покупателя. | Другой аккаунт владельца и другое устройство не имеют доступа к этому хранилищу. | Локальный заказ, который выдаётся за заказ магазина или должен попасть в админку. |
| URL из бота мог вести на старый Vercel runtime, а GitHub Pages уже содержал новый код. | Покупатель и разработчик проверяют разные версии приложения. | Два равноправных production-адреса без одного канонического URL и live-проверки. |
| `order-api` в подключённом Supabase-проекте отвечал `404`. | Общий серверный заказ невозможно создать. | Кнопка оформления, которая сообщает об успехе без ответа сервера. |
| Ошибка `trackOpen()` скрывалась пустым `catch`. | Новый пользователь может не попасть в админку, а причина теряется. | Тихая потеря событий пользователей и заказов. |
| Серверные каталог, пользователи и заказы находились на разных стадиях готовности. | Интерфейс выглядит связанным, но данные не имеют общей гарантированной точки истины. | Отдельные источники истины для каталога, покупателя и админки. |

## 3. Главный принцип проекта

**Mini App и админ-панель — не две базы и не две отдельные панели.** Это два интерфейса над одними серверными сущностями в Supabase.

```text
Покупательский Mini App ─┐
                         ├── Edge Functions ─── Supabase Postgres / Storage
Админ-панель владельца ──┘
                                   ↑
                              Bot / payment webhook
```

`localStorage` допустим только как временное удобство текущего устройства. Он не может быть источником истины для общего каталога, остатков, пользователей, заказов, оплаты или статуса сборки.

## 4. Что обязательно должно быть в нашем магазине

### 4.1 Один источник данных

- Опубликованные товары, варианты, фотографии, остатки, пользователи, заказы и статусы хранятся в Supabase.
- Покупательский каталог получает только опубликованные товары через `catalog-api`.
- Админка получает товары, пользователей и заказы только через защищённые серверные функции.
- После создания, публикации, изменения остатка, оформления заказа или смены статуса интерфейс берёт итог из ответа сервера, а не «догадывается» локально.
- У проекта есть один канонический URL Mini App; именно он указан у бота, проверяется после публикации и используется в документации.

### 4.2 Пользователь

- При открытии приложения внутри Telegram `user-api` проверяет raw `Telegram.WebApp.initData` на сервере и сохраняет/обновляет `customers`.
- Телеграм-ID покупателя берётся только из проверенного `initData`, а не из `initDataUnsafe` и не из поля, пришедшего от браузера.
- Повторное открытие не создаёт бесконечные дубли: фиксируется первое открытие, последнее открытие и максимум одно служебное событие открытия в день.
- Создание заказа дополнительно обеспечивает наличие пользователя в `customers`, даже если отдельное событие открытия не дошло.
- В админке видны только данные, нужные владельцу магазина: имя Telegram, username при наличии, даты активности, факт оформления заказа. Никаких секретов, токенов или лишней истории пользователя.

### 4.3 Каталог и товар

- Один товар/цвет/размер имеет серверный ID и актуальный остаток.
- Опубликованный товар появляется в buyer-каталоге из `catalog-api`; черновик и архив покупателю не видны.
- После публикации, архивации или изменения остатка админка получает подтверждённый серверный результат, затем buyer-каталог обновляется.
- На другом устройстве каталог обновляется при возвращении в Mini App и через ограниченную проверку свежести. Настоящий realtime допустим только отдельным безопасно спроектированным этапом.
- Товар с нулевым остатком может быть показан для просмотра, но его вариант нельзя добавить в корзину.

### 4.4 Корзина и заказ

- Корзина может храниться локально до подтверждения, но созданный заказ обязан появляться в Supabase.
- Клиент отправляет только ID товара, ID варианта, количество, выбранный способ получения, контакты и идемпотентный ключ.
- Сервер сам читает цену, название, вариант, доступность и остаток из БД. Цена, итог, скидка, статус и остаток, пришедшие из браузера, не являются достоверными.
- Повторное нажатие, плохая сеть или повтор запроса с тем же idempotency key не создают два заказа.
- Корзина очищается только после успешного ответа сервера.
- Покупатель видит только свои заказы; владелец — общую очередь; один покупатель никогда не может открыть заказ другого по подменённому ID.

### 4.5 Демо-оплата сейчас

- Демо-оплата — это серверный тестовый заказ, а не локальная имитация.
- Он хранится в `orders` и `order_items`, появляется у покупателя, владельца и в карточке пользователя.
- У него есть явная серверная метка `demo`/`payment_mode: demo`, видимая владельцу как «Демо-оплата».
- Покупатель может увидеть нейтральный текст «Заказ принят», но интерфейс не сообщает, что получены реальные деньги.
- Демо-заказ не уменьшает остатки и не запускает настоящее платежное уведомление.
- Владелец может перевести тестовый заказ в «Собран» только через серверную проверку прав. Это изменение сохраняется в БД и появляется на других устройствах.

### 4.6 Реальная оплата позже

- Нажатие «Оплатить» не делает заказ `paid`.
- Клиент открывает платёжную форму/инвойс провайдера, но не доверяет только возврату пользователя на экран успеха.
- Подтверждение оплаты приходит от провайдера в отдельную Edge Function webhook.
- Webhook проверяет подпись по сырому телу запроса, обрабатывает событие идемпотентно и только затем переводит заказ в `paid`.
- Только после подтверждённого платежа можно уменьшать остаток, отправлять уведомление владельцу и переводить заказ в рабочую очередь оплаты.
- Секрет webhook и service-role ключ живут только в серверных Secrets, никогда в `tg-app/`, Git или браузере.

### 4.7 Статусы и уведомления

Для первого магазина достаточно такой понятной цепочки:

```text
demo → ready                 тестовая демо-оплата
pending_payment → paid → ready  будущая настоящая оплата
любое допустимое состояние → cancelled  отмена с причиной
```

- Каждый переход проверяет сервер: кто его выполняет, из какого статуса и в какой.
- Статусы покупателя формулируются по-человечески: «Заказ принят», «Оплата подтверждена», «Заказ собран», «Заказ отменён».
- После подтверждённого серверного события можно отправлять уведомление владельцу и покупателю. Повтор webhook/повтор действия не должен создать двойное уведомление.

### 4.8 Безопасность и наблюдаемость

- `admin-api`, `order-api`, `user-api` проверяют raw Telegram `initData` на сервере; доступ владельца дополнительно проверяется allowlist.
- В браузере нет `BOT_TOKEN`, `service_role`, платёжных секретов, реальных Telegram ID владельца и сырых `initData` в логах.
- RLS включён на открытых таблицах. Напрямую из браузера не читаются чужие заказы, покупатели и служебные события.
- Ошибки не проглатываются. Покупатель получает безопасное понятное сообщение; разработчик получает код ошибки/контекст без персональных данных и секретов.
- У каждой Edge Function есть проверка, что она реально развёрнута: закрытые функции без `initData` отвечают `401`, а не `404`; публичный каталог отвечает `200`.

### 4.9 Качество и выпуск

- Перед выпуском проходят синтаксические проверки, клиентские тесты, серверные контрактные тесты и `git diff --check`.
- Отдельно проверяются два Telegram-аккаунта: покупатель и владелец.
- После push сверяется SHA локального коммита и `origin/main`.
- После deploy проверяется live HTML и JS по URL, открываемому ботом, с cache buster.
- Browser/Node-проверки не называются проверкой Telegram iOS/Android, пока не выполнен реальный device smoke-test.

## 5. Чего в проекте не должно быть

| Нельзя | Почему |
| --- | --- |
| Локальный демо-заказ как единственный «заказ магазина». | Он не синхронизируется между пользователем, владельцем и устройствами. |
| Клиентская установка `paid`, цены, суммы, остатка или статуса заказа. | Эти поля можно подменить из браузера. |
| Уведомление о реальной оплате по факту нажатия кнопки. | Нажатие не является платежом. |
| Два разных production URL, один из которых открывает бот, а второй проверяет разработчик. | Это создаёт ложные результаты проверки и старый runtime у покупателей. |
| Пустой `.catch(() => {})` вокруг действий, влияющих на пользователей и заказы. | Ошибки исчезают, а данные не появляются. |
| Прямой доступ браузера к таблицам покупателей, заказов и служебных событий. | Риск утечки персональных данных и изменения чужих заказов. |
| Service-role, BOT_TOKEN, webhook secret, raw `initData` в коде, Git или отчётах. | Это компрометация магазина и аккаунтов. |
| Списание остатка за демо-заказ или до подтверждённого платежа. | Тестовая операция не должна влиять на реальный товар. |
| Бесконечный polling и параллельные запросы для имитации realtime. | Это создаёт нагрузку, дубли и нестабильный интерфейс. |
| Объявление функции «работающей» по локальному тесту, если Edge Function не развёрнута или Telegram-flow не проверен. | Локальный код и production — разные среды. |

## 6. Контрольный список соответствия требованиям

Этот список предназначен для оценки будущей реализации, а не для автоматического старта работ.

- [ ] У бота один канонический URL, и он отдаёт текущий commit/assets.
- [ ] Все published товары и их остатки берутся из Supabase, а не из локальной панели.
- [ ] Новый Telegram-пользователь появляется в серверной `customers`.
- [ ] Заказ создаётся на сервере и доступен покупателю и владельцу на разных аккаунтах.
- [ ] Демо-заказ помечен как демо, не как реальная оплата.
- [ ] Повтор нажатия не создаёт второй заказ.
- [ ] Админка показывает серверные заказы и пользователей, а не локальный снимок браузера.
- [ ] Смена статуса заказа хранится на сервере и синхронизируется.
- [ ] Публикация/изменение товара в админке появляется у покупателя.
- [ ] Реальный платёж подтверждает только webhook провайдера.
- [ ] Нет клиентских секретов, прямого доступа к чужим данным и тихо подавленных ошибок.
- [ ] Проверка пройдена на двух Telegram-аккаунтах и на live URL бота.

## 7. Как использовать этот документ

Перед изменением checkout, оплаты, пользователей, очереди заказов, каталога или публикации товара агент сначала сверяет решение с разделами 4 и 5. Если предлагаемое изменение нарушает хотя бы один пункт «не должно быть», его нельзя внедрять как временное упрощение без отдельного решения владельца.

Перед реализацией нужно отдельно согласовать объём первой серверной итерации: она должна закрыть общий каталог, пользователей и серверные демо-заказы. Настоящий провайдер оплаты и Supabase Realtime остаются отдельными, явно утверждаемыми этапами.
